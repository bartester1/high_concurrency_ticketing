高併發搶票架構 — 10 萬人同時搶

核心機制：入口層把流量削成下游吃得下的速率，Redis Lua 原子扣票，DB 只做最後裁決與記帳。Redis 是前置過濾器、不是 source of truth，正確性由 Spanner 的 UNIQUE 約束與對帳保證。本文為設計草案，未做任何壓測。

PART 1

流程圖解

先看判定規則，再看三張圖：請求怎麼流、Lua 怎麼判、訂單狀態怎麼轉。

1核心規則

Redis Lua 的回傳值決定一切，API 層只翻譯結果，不自己判斷庫存。

Lua 回傳 / 情況API 行為為什麼
1 扣票成功發 hold token，導向付款hold 帶 TTL，沒付款自動失效，庫存靠 reaper 補回
2 同 token 重送回上次結果，不再扣使用者連點、網路重試都不能多扣
-2 超過限購回 4xx，不扣限購在扣票同一個原子步驟內判，才不會被併發繞過
-1 庫存不足回「已售完」，不扣不進 DB、不排隊，直接結束
Redis 逾時 / failover失敗關閉：回 503 + Retry-After，不放行

為什麼寧可少賣、不能超賣

Redis 主從切換或 AOF everysec 可能丟最後一秒資料，庫存計數會失準。少賣可以靠對帳補回，超賣已經收錢就只能退款。所以 Redis 無法判斷時一律拒絕，而不是放行賭一把。

2請求路徑

看這張圖抓一件事：DB 在最後面，使用者請求走完 Redis 就結束，Spanner 的寫入是非同步的。

3Lua 原子扣票判定

四步在同一個 Lua 裡完成，Redis 單執行緒保證中間不會被插隊。順序固定：冪等 → 限購 → 庫存 → 扣。

4訂單狀態機

看這張圖抓晚到的付款 callback：hold 過期後才收到付款成功，票可能已被別人拿走，必須走退款。

5庫存分片與 reaper 補回

看這張圖抓兩件事：扣票只打 hash(uid) mod N 固定映射的那一片，售罄就是售罄、不換片；補回庫存必須回到當初扣的那一片，所以 holds ZSET 要按分片拆成 holds:{i}，否則分片計數會漂移。

分片的兩個坑

  • 補回回錯片：ZSET 按分片拆成 holds:{i}，Reaper 掃哪一片就 INCRBY 那一片的 stock:{i}。
  • 「已售完」只代表該使用者那一片：其他分片可能還有票，但不能讓使用者換片，否則限購會被繞過。uid 分佈不均時，某片會先售罄而別片有餘，各片庫存怎麼配（或要不要再平衡）尚未拍板。
  • N 上線後不可改：改 N 會讓 uid 換片，原本的 bought:{i}:<uid> 計數就對不上。

6報名抽籤制

看這張圖抓一件事：報名階段只收單、不扣庫存，所以沒有搶庫存的競態；扣庫存只發生在抽完籤之後，且只對中籤者做。峰值從「開賣瞬間」變成「報名窗口內的寫入」。

PART 2

規格

每一層負責什麼、Lua 怎麼寫、付款與過期的邊界怎麼處理。

7分層防線

每層只擋自己能擋的，漏過的交給下一層。越前面越便宜、越後面越準。

層做什麼為什麼
邊緣活動頁靜態化丟 CDN；WAF；排隊前先登入 + Turnstilebot 若先進排隊就佔掉名額，後端再快也沒用
排隊放行速率 = 下游容量（token bucket）；位置用 SSE / WebSocket 推送10 萬人輪詢排隊頁會自己先倒；重試一律 exponential backoff + jitter
RedisLua 原子扣票；熱門庫存拆成 N 個 key 分片單一 key 全打同一個 slot，Cluster 也救不了；分片數靠壓測決定
佇列事件進 Stream / Pub-Sub，Worker 批次寫 DB，消費冪等削峰；Worker 掛掉要能重送，所以寫入必須冪等
DBUNIQUE(event_id, seat_id) 或 UNIQUE(order_id)；定時對帳最後一道閘：Redis 丟資料時，DB 拒絕重複成交；對帳：庫存 + hold + 已成交 = 總量
提醒降級：超過容量直接 429 / 503 + Retry-After排隊吃記憶體比拒絕更危險；只提醒，不影響上面各層

8Lua 腳本

Lua（Redis EVAL）示意，未在實際 Redis 跑過
-- KEYS[1]=stock:{i}  KEYS[2]=bought:{i}:<uid>  KEYS[3]=hold:{i}:<token>  KEYS[4]=holds:{i}
-- i = hash(uid) mod N，由 API 算好再組 KEYS；同一 uid 永遠同一片
-- ARGV[1]=qty  ARGV[2]=limit  ARGV[3]=ttl_sec  ARGV[4]=expire_ts  ARGV[5]=uid  ARGV[6]=token
if redis.call('EXISTS', KEYS[3]) == 1 then return 2 end
local bought = tonumber(redis.call('GET', KEYS[2]) or '0')
if bought + ARGV[1] > tonumber(ARGV[2]) then return -2 end
local s = tonumber(redis.call('GET', KEYS[1]) or '0')
if s < tonumber(ARGV[1]) then return -1 end
redis.call('DECRBY', KEYS[1], ARGV[1])
redis.call('INCRBY', KEYS[2], ARGV[1])
redis.call('SET', KEYS[3], ARGV[1], 'EX', ARGV[3])
-- member 帶 uid 與 qty：hold key 的 TTL 到了就沒了，Reaper 補回時只能靠這裡
redis.call('ZADD', KEYS[4], ARGV[4], ARGV[6] .. ':' .. ARGV[5] .. ':' .. ARGV[1])
return 1

分片時：四個 KEYS 在 Redis Cluster 必須落在同一個 slot，所以全部用同一個 hash tag {i}，否則 EVAL 會被拒絕。其中 i = hash(uid) mod N 由 API 先算好，同一個 uid 永遠落在同一片，所以 bought:{i}:<uid> 就是該 uid 的完整限購計數。

9Hold 過期與付款的競態

「10 分鐘沒付錢自動 release」的邊界最容易出事。下表是各情況的處理，狀態轉換一律用 CAS（比較後更新）。

層情況處理 / 為什麼
共用Lua 扣票成功同一個 Lua 內 ZADD holds:{i}，member = token:uid:qty。ZSET 按分片拆，i 由 hash(uid) 固定，Reaper 掃哪一片就補哪一片，限購計數也在同一片一併退；hold key 有 TTL 會消失，所以 uid 與 qty 必須放在 member 裡
共用使用者按下付款HELD → PAYING，延長 TTL，並 ZADD XX 把 holds:{i} 的 score 改成延長後的時間。付款中的單不能被 reaper 掃掉，否則剛輸入完卡號票就沒了
共用hold 到期且未付款HELD → EXPIRED。Reaper 對每個 holds:{i} 取 score ≤ now，CAS 成功才 INCRBY stock:{i} 並 DECRBY bought:{i}:<uid>。限購計數也要退，否則使用者放棄後額度永久少一份；不依賴 keyspace notification，它不保證送達
Reaper補回到一半掛掉順序固定：先 CAS 狀態、成功才補庫存、最後才 ZREM。重跑時 CAS 失敗就只 ZREM，不會重複補回
硬擋付款成功 callback 到達，但狀態已是 EXPIRED 且票已被別人拿走走 REFUND，不可硬塞一張票；Cloud Tasks delayed task 當 reaper 的兜底
Worker同一事件被消費兩次以 order_id 冪等寫入，UNIQUE 約束擋重複
提醒對帳發現 Redis 庫存與 DB 不一致只告警並人工確認，不自動修正庫存

10現況與待決

已驗證

  • 無。本文為設計草案，Lua、分片、reaper 都未實測。
  • 單 key 的 ops 上限、放行速率都只能靠壓測得到，文中沒有引用任何效能數字。

給實作者的一句話規格

  • Redis 只做前置過濾，DB 的 UNIQUE 與對帳才是正確性來源。
  • 查票、限購、扣票、記 hold 在同一個 Lua。
  • Redis 無法判斷時回 503，不放行。
  • 付款中延長 TTL；過期後晚到的付款走退款。

未拍板

  • 誰決定：放行速率 <N/s>，需依下游壓測結果。
  • 誰決定：庫存分片數 <N>。
  • 誰決定：各分片庫存怎麼配、uid 分佈不均造成某片先售罄時要不要再平衡；N 與 hash 函式也要在上線前定死。
  • 誰決定：搶票制或報名抽籤制。抽籤制：報名只收單、沒有庫存競態，峰值變成窗口內的寫入，也沒有「先到先得」的公平爭議；代價是購票不即時（要等開獎）、要另做候補與逾期遞補、沒有「搶到」的體驗。搶票制：即時、體驗直接，但峰值、超賣風險和 bot 壓力都集中在開賣瞬間，本文圖 1–4 的複雜度主要來自這裡。
  • 誰決定：hold TTL（暫定 10 分鐘）與 PAYING 延長值 <分鐘>。
  • 業務是否改成報名抽籤制，可直接消掉峰值。
